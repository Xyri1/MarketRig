# OpenViking continuity — Feature Decisions

Local decisions for [slice 011](../../slices/011-openviking-migration.md), prefixed `OV-<n>`. They settle the product decisions taken on 2026-09-07 into mechanics and name the root decisions they supersede; on merge they are summarized as one product `D<n>` and the superseded entries are edited in place. OpenViking facts were verified on 2026-09-07 against the `openviking` 0.4.17.1 wheels on PyPI and the `main` branch of `volcengine/OpenViking`; Claude Code and Codex facts against their current documentation the same day.

### OV-1 — Hindsight is removed; two operator-named prerequisites and one private environment provisioned offline from bundled wheels

**Decision:** Every Hindsight mechanism is deleted: the `memory_child` row and its discover, retry, and launch paths, the derived banks, the four `marketrig memory` commands and their routes, `memory-standin`, and G33–G37 and E5 in their present form. Nothing reads a `<data root>/hindsight/` directory. Setup is one installation resource, `openviking_setup`, holding an operator-named absolute Python path and an operator-named absolute Node path, each validated by running it: Python must report exactly `3.12`, the minor upstream builds its wheels on and tests on both MVP platforms, never a range inferred from OpenViking's `>=3.10`; Node must report major 22 or above, the runtime the Codex plugin names. The provider save also measures the embedding model's dimension once, because OpenViking silently assumes 2048 for a model it does not know. Provisioning creates `<data root>/openviking/venv` with the validated interpreter's own `venv` module and installs `openviking==0.4.17.1` with `pip --no-index --find-links` from the per-platform wheel directory the release unit carries beside the daemon, so the install needs no network and no compiler. The provider row keeps its shape — one OpenAI-compatible base URL, key in the credential store, one VLM model, one embedding model — and its `PUT /memory/provider` route.

**Rationale:** The project has no released users, so a compatibility path buys nothing and costs a second memory system in every scenario. The user chose a user-installed Python and Node over bundled runtimes; validating by running the named executable is the shape R3 uses for the runtimes and R4 used for the launcher. One validated minor is the only claim the wheel validation actually supports. `--no-index` is what turns "bundled wheels" into a property the checks can assert. OpenViking is AGPL-3.0 and so is MarketRig (root §4.1), so bundling raises no licensing question; the bundle carries the wheels unmodified with their license texts.

`ponytail:` one minor, one venv location, and pip over the bundled directory. The interpreter search exists as `GET /openviking/candidates` ([SPEC](SPEC.md) §1.1): a fixed per-platform list of places 3.12 and Node install, each candidate accepted or refused by §1.2's own validators, which is why it adds no second notion of "supported". A range of minors or a uv-driven install still arrives as a wider validation matrix behind the same setup route.

**Contract:** root [SPEC §4.1](../../SPEC.md#41-installation), [§4.4](../../SPEC.md#44-configuration-scopes); this feature's [SPEC](SPEC.md) §1.

### OV-2 — One `openviking-server` child starts with the daemon, answers `/ready`, and is `UNAVAILABLE` on its first loss

**Decision:** When `openviking_setup` is `AVAILABLE` and the provider row is complete, daemon startup — after recovery, before the listener accepts desk work — spawns `<venv>/bin/openviking-server --config <data root>/openviking/ov.conf --host 127.0.0.1 --port <port>` under the containment primitive, records it in `runtime/children.json`, and polls `GET /ready` every 500 ms within 120 s. The daemon writes `ov.conf` before every start: strict JSON, `server.root_api_key` and the provider `api_key` fields as `${…}` references that OpenViking's loader expands from the child's environment, so no secret is in the file; `storage.workspace` under `<data root>/openviking/data`, local AGFS and vector backends, the provider's VLM and embedding sections, `memory.session_skill_extraction_enabled: false`. Readiness appends `OPENVIKING_STARTED`; the child exiting, or the deadline passing, appends `OPENVIKING_LOST` and sets the row `UNAVAILABLE` with the last output line — there is no automatic restart — and `POST /openviking/retry` starts it once more. Stop is `SIGTERM`, 3 s, then the group kill; on Windows the plain kill. A startup failure never delays or blocks desks, triggers, trading, or sessions.

**Rationale:** The user settled start-with-daemon and no automatic restart. `/ready` is the endpoint that checks storage, key manager, and embedding, so it is the readiness the plugins need, where `/health` is liveness only. The `${VAR}` expansion is documented loader behavior and is how OpenViking's own Helm chart injects the root key, and it keeps both secrets out of the data root. OpenViking documents no graceful-shutdown contract; uvicorn honors `SIGTERM`, and task records are persisted, so a pending extraction is a `failed` task the docs describe, never an invented retry.

`ponytail:` fixed 120 s deadline and one config layout; a per-machine measured deadline or a config the operator edits arrives when a real machine misses it.

**Contract:** root [SPEC §4.4](../../SPEC.md#44-configuration-scopes), [§4.6](../../SPEC.md#46-daemon-startup-and-shutdown), [§16](../../SPEC.md#16-memory-and-skills); this feature's [SPEC](SPEC.md) §2.

### OV-3 — `api_key` mode, account `marketrig`, one user per desk with a seed-derived key held in the credential store's one installation secret

**Decision:** The child runs in `api_key` mode behind a 32-byte hex root key minted per start and held in daemon memory only. The daemon keeps one installation secret, `openviking_seed` (32 random bytes, hex), in the OS credential store, created on first provisioning. At every child readiness it ensures account `marketrig` exists and, for every `READY` desk, the user `desk-<uuid hex>`; a desk created while the child is ready is provisioned at creation's end. Each user's key is obtained by `POST /api/v1/admin/accounts/marketrig/users/{user}/key {seed}`, which is deterministic per OpenViking's documented `sha256(user_id + "\0" + seed)` — so the same call after a restart or Retry yields the same key and a session started earlier keeps working — and the key is held in memory only, per desk. An `AlreadyExists` on account or user creation is success. Desk keys and the root key never enter SQLite, a log, an event, a prompt, CLI output, or any workspace file.

**Rationale:** In `dev` mode every caller is ROOT with no user binding, so isolation would rest on the plugin's own URI discipline; in `api_key` mode a user key reaches only that user's data and ROOT cannot read tenant data. The seed makes "regenerate at every start" and "never persist a key" compatible with sessions that outlive a child restart — without it, Retry would strand every live session's hooks. The seed is a provider-secret-shaped fact and goes where those go (per D49).

`ponytail:` one account and one flat user per desk; peers, workspaces, and shared `viking://agent/skills` stay unused until a scenario needs cross-desk material.

**Contract:** root [SPEC §4.4](../../SPEC.md#44-configuration-scopes), [§16](../../SPEC.md#16-memory-and-skills); this feature's [SPEC](SPEC.md) §3.

### OV-4 — The upstream plugins are vendored unmodified, seeded per desk, registered through the launch files, and configured through the runtime's process environment

**Decision:** MarketRig ships OpenViking's `examples/claude-code-memory-plugin` and `examples/codex-memory-plugin` (with the shared library copies they already contain) unmodified, at the upstream commit SPEC §4 pins, under `crates/marketrigd/seed/openviking/`. Desk creation copies them to `<workspace>/.marketrig/plugins/openviking-claude/` and `openviking-codex/`, MarketRig-owned and reconciled byte for byte at startup like the `CLAUDE.md` shim. Registration is the daemon's existing launch files: for Claude Code the `--settings` file gains the plugin's `hooks.json` entries with `${CLAUDE_PLUGIN_ROOT}` replaced by the seeded absolute path and `node` replaced by the validated Node path, and the `--mcp-config` file gains `openviking` running the seeded `servers/mcp-proxy.mjs`; for Codex, `<workspace>/.codex/config.toml` gains `[mcp_servers.openviking-memory]` and `<workspace>/.codex/hooks.json` is written from the plugin's `hooks.json` the same way. Configuration is environment on the runtime process, inherited by every hook and by the proxy: `OPENVIKING_URL`, `OPENVIKING_API_KEY` (the desk key), `OPENVIKING_ACCOUNT=marketrig`, `OPENVIKING_USER=<desk user>`, `OPENVIKING_HOME=<data root>/openviking/plugin/<desk-id>/` (state, pending queue, workspace registry, and log all resolve under it), `OPENVIKING_CONFIG_FILE` and `OPENVIKING_CLI_CONFIG_FILE` pointing at absent files under that directory so the user's `~/.openviking` is never read, and `OPENVIKING_MEMORY_ENABLED=1`. The registration and the environment exist exactly when the daemon holds the desk's key: setup not `AVAILABLE`, a child still `STARTING`, or a child lost (the keys are dropped at loss, §2.3) all launch with `OPENVIKING_MEMORY_ENABLED=0` and no registration, because without `OPENVIKING_API_KEY` the hooks and the proxy have nothing to queue with; a session launched while `READY` keeps its key across a later loss, and the plugin's own pending queue holds its captures until Retry. The agent's memory operations are the plugin's MCP tools; `marketrig` has no memory command; `marketrig-mcp` proxies nothing. Skill writes are the one exception (OV-5): OpenViking's MCP `write` and `edit` refuse the managed `skills/` subtree (`openviking/storage/content_write.py`, `_USER_MANAGED_SUBTREES`, verified 2026-09-07 on 0.4.17.1), and no MCP tool creates a skill, so the agent writes a skill through `marketrig skill put`, which the daemon forwards to `POST`/`PUT /api/v1/skills` under the desk key.

**Rationale:** The user chose the upstream plugins for capture, recall, and the agent's tools, shipped locally and seeded project-scoped. Verified facts fix the rest: the plugin resolves its URL and key from environment first, and its workspace config layer strips `url`, `api_key`, `account`, and `user`, so a key in a workspace file would be ignored — the process environment is the only per-desk path that exists, and it is the same path R4 already granted the Hindsight child (per D49). The daemon owns every runtime launch, so it owns that environment. Both runtimes' launch files already exist and already carry `marketrig`'s own hooks and MCP server, so registration adds entries to files the daemon writes and deletes anyway, with no plugin-manager install, no marketplace, and no user-level Codex or Claude configuration touched. Unmodified vendoring keeps the upstream fix path open and the byte-for-byte reconcile honest.

Codex specifics, from its current documentation and source: a project `.codex/hooks.json` loads only for a trusted project layer, which R3's `config.toml` already requires; every non-managed hook is skipped until its exact definition is trusted, and `--dangerously-bypass-hook-trust` is a shared CLI option honored by `codex` and `codex resume`, so the daemon's launch carries it; hooks are on by default and `plugin_hooks` is a removed feature key; `command` is one string with a `commandWindows` variant; `${PLUGIN_ROOT}` is expanded only for plugin-managed hooks, so the daemon substitutes the absolute path itself.

`ponytail:` the plugin version is one vendored commit; upgrading it is a seed change verified by the reconcile check.

**Contract:** root [SPEC §4.4](../../SPEC.md#44-configuration-scopes), [§5.1](../../SPEC.md#51-workspace-ownership), [§6.4](../../SPEC.md#64-runtime-adapter-contract), [§13](../../SPEC.md#13-agent-surface), [§16](../../SPEC.md#16-memory-and-skills); this feature's [SPEC](SPEC.md) §4.

### OV-5 — OpenViking owns skills; `.agents/skills/` is a MarketRig-owned read-only projection refreshed before every activation and after every turn; the improvement skill is seeded into the desk's user

**Decision:** A desk's skills are `viking://~/skills/<name>/` under its user. Before every activation, new or resume, and after every `SESSION_TURN_ENDED`, the daemon lists the user's skills, fetches each with content and auxiliary files, and rewrites `.agents/skills/` to match exactly: one directory per skill with `SKILL.md` and its files, directories for absent skills removed, files `0444` and directories `0555` on macOS and read-only attributes on Windows, the `.claude/skills` link kept as today. A projection failure — child not ready, a fetch error — leaves the last projection in place, appends `SKILLS_PROJECTION_FAILED`, and never blocks the activation. The agent writes a skill with `marketrig skill put <desk> --file <SKILL.md>` (the name from the frontmatter; the daemon `POST`s or `PUT`s `/api/v1/skills` under the desk key and refreshes the projection before answering) and removes one with `marketrig skill delete <desk> <name>`; OpenViking's own `write` and `edit` tools refuse the `skills/` subtree, and `forget` is not used for skills. A direct edit to the projection is refused by the filesystem and the constitution says so. `session_skill_extraction_enabled` is `false`. Desk provisioning uploads the seeded `desk-improvement` skill through `POST /api/v1/skills` under the desk's key, skipped when a skill of that name exists; the seed stays a file under `crates/marketrigd/seed/` compared byte for byte. The constitution is rewritten for the plugin's tools and the projection rule; `CLAUDE.md` is unchanged.

**Rationale:** OpenViking has no export of skills to a filesystem, its plugins only annotate a locally read `SKILL.md` with experience, and both runtimes discover skills only from files — so the projection is the one piece neither side provides. Refreshing at turn end covers OpenViking-side changes the daemon does not make; a `marketrig skill` write refreshes at once. The CLI is the only write path because OpenViking exposes skill creation on REST alone, and the desk key lives only in the daemon and the runtime environment, so the daemon forwarding it is the path that keeps the key out of the agent's hands and the projection current (per D4, the continuity plane is the CLI). Read-only files are the cheapest way to make "one canonical owner" true; a write the runtime cannot make is one the projection cannot lose. Extraction stays off by decision: only the agent writes skills. Seeding into OpenViking rather than the tree keeps a single owner from the first activation.

This supersedes D19's file-owned procedural layer, D20's "agent-owned seed material is never rewritten", and D21's "MarketRig does not copy or synchronize a second skill tree" for the skills directory alone; the link rule of D21 stands.

`ponytail:` full rewrite of the tree on every refresh; a content-hash diff arrives when a desk's skill set makes the rewrite measurable.

**Contract:** root [SPEC §2](../../SPEC.md#2-canonical-terminology), [§5.1](../../SPEC.md#51-workspace-ownership), [§5.2](../../SPEC.md#52-creation-and-recovery), [§7](../../SPEC.md#7-activation), [§16](../../SPEC.md#16-memory-and-skills); this feature's [SPEC](SPEC.md) §5.

### OV-6 — Migration 7: the setup row replaces the child row, memory events become OpenViking events, and recovery needs no new step

**Decision:** Migration 7 drops `memory_child`, creates the one-row `openviking_setup` (§1), keeps `memory_provider` as is, deletes every `MEMORY_*` operational event, and rebuilds `operational_events.kind` without the six `MEMORY_*` kinds and with `OPENVIKING_CONFIGURED`, `OPENVIKING_PROVISIONED`, `OPENVIKING_STARTED`, `OPENVIKING_LOST`, `OPENVIKING_UNAVAILABLE`, `DESK_MEMORY_PROVISIONED`, `SKILLS_PROJECTED`, and `SKILLS_PROJECTION_FAILED`. The child's live state, the root key, and the desk keys live in memory only; the child is a `children.json` record the first recovery step already reaps.

**Rationale:** No compatibility is owed to Hindsight rows, and a kind widening is already a table rebuild (root §15), so dropping the old kinds costs nothing extra. Everything transient stays transient, as R4 decided for the same reasons.

**Contract:** root [SPEC §15](../../SPEC.md#15-persistence-crash-recovery-and-history); this feature's [SPEC](SPEC.md) §6.

### OV-7 — The gate runs `openviking-standin`; the experiment attends real OpenViking and the real plugins

**Decision:** The harness's memory helper becomes `openviking-standin`: registered as the child by explicit path through the setup route's test seam, it serves `/health`, `/ready`, the admin account, user, and seeded-key routes, the skills routes, sessions with messages and a scripted commit task, `find`, and `content/read`, on the exact paths and field shapes the daemon consumes, behind `api_key` auth over an in-memory per-user store, with its readiness delay and scripted exit from the `openviking` object of `MARKETRIG_STANDIN_SCRIPT`. G33–G37 are replaced by O1–O6 (SPEC §7.2); E5 is replaced by E6, which needs the validated Python and Node, the bundled wheels, and a real provider, and skips with evidence without them. The gate never runs Node, Python, or a hook script.

**Rationale:** The deterministic gate proves MarketRig's mechanics — startup, provisioning, projection, loss, secrets — which need only the HTTP subset; the plugins' behavior is upstream's and is evidence only under a real runtime, which is the experiment's job (per D75).

**Contract:** root [SPEC §17](../../SPEC.md#17-verification); this feature's [SPEC](SPEC.md) §7.
