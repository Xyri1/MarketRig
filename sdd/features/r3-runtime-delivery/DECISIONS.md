# R3 — Runtime adapters and delivery: Feature Decisions

Local decisions for [Milestone R3](../../ROADMAP.md#milestone-r3--runtime-adapters-and-delivery), prefixed `R3-<n>`. They resolve mechanics the root SPEC defers (§18) for R3's scope and contradict nothing settled; on merge they are summarized as one product `D<n>` in `sdd/DECISIONS.md`. Runtime facts were verified on 2026-09-02 against Codex CLI 0.152.1 (`codex app-server generate-json-schema`, the app-server README) and Claude Code 2.1.258 (the channels and hooks references at code.claude.com); those are the version floors.

### R3-1 — A runtime target is one installation row: an exact executable, its version, and a validation outcome

**Decision:** `runtimes` holds one row per runtime (`codex`, `claude`) with `executable_path`, `version`, `state` (`UNDISCOVERED | AVAILABLE | UNAVAILABLE`), `validated_at_ns`, and a failure code and message. Discovery runs at daemon start for every `UNDISCOVERED` row and on `POST /runtimes/{runtime}/discover`, which takes an optional explicit `executable`; without one the daemon resolves the bare name through the user's real environment: on macOS the login shell's `PATH`, captured once per daemon start by running the user's `$SHELL -l -c 'printf %s "$PATH"'` with a 10-second timeout and kept only in memory; on Windows the user and machine `PATH` read fresh from the registry, accepting `.exe`, `.cmd`, and `.bat` and launching the latter two through `%ComSpec% /d /c`. Validation runs `<executable> --version`, parses the first dotted version, and requires Codex `>= 0.152.1` and Claude Code `>= 2.1.258`; Claude additionally requires `--dangerously-load-development-channels` and `--settings` in `--help`, Codex additionally requires the `app-server` subcommand. An explicit executable that fails validation leaves the row `UNAVAILABLE` with the reason and is not launched. The `state` a control-plane loss sets (R3-3) lives on the same row, so one read answers "can this runtime be launched now".

**Rationale:** D25 separates discovery from shell policy and forbids a command shell around the session; capturing `PATH` once and launching directly is exactly that. Version floors are the only capability probe that is both cheap and honest: the flags and subcommands the adapters need exist at these lines and were exercised in this design.

`ponytail:` version parsing is the whole capability check. Replace it with a real protocol probe (`initialize` on a throwaway app-server, a `--print` hook round trip) if a future line keeps the flags but changes their meaning.

**Contract:** root [SPEC §4.4](../../SPEC.md#44-configuration-scopes); this feature's [SPEC](SPEC.md) §2.

### R3-2 — One terminal manager over `portable-pty`, one WebSocket attachment route, no spawn helper

**Decision:** The terminal manager is one private daemon module over `portable-pty =0.9.0` (MIT, the wezterm PTY crate; `openpty` on macOS, ConPTY on Windows). Each terminal is spawned through the crate's `CommandBuilder` with the desk workspace as cwd and the environment R3-3 or R3-4 composes; the crate's Unix spawn is `std::process::Command` with a `pre_exec` that only calls `setsid` and `TIOCSCTTY` before `exec`, which is the fork-then-exec-only pattern and needs no single-threaded spawn helper. One blocking reader thread per terminal drains the master into a 256 KiB reconnect ring and the current attachment; a bounded writer channel carries input; resize requests coalesce to the newest size. The attachment is `GET /desks/{desk_id}/terminal` upgraded to a WebSocket through axum's `ws` feature: binary frames are raw bytes in both directions, one text frame `{"resize":{"cols":n,"rows":n}}` resizes, the server sends the ring then live bytes, a new attachment invalidates the previous one with a close frame `4001 superseded`, and process end sends `{"exited":{"reason":"<exit_reason>","code":n|null}}` then closes. Shutdown stops input, drains output for up to 2 seconds, terminates the contained process tree through the R2 primitive, and joins the reader. Nothing is persisted.

**Rationale:** D31 asks for one owner and one pinned crate; `portable-pty` is the maintained cross-platform choice with the ConPTY half already proven in wezterm, and its spawn path answers the fork-safety question without a helper. The socket exists now because the acceptance harness must attach to answer a real runtime's own dialogs, and R5's desktop needs the same route.

`ponytail:` one reader thread per terminal, not an async reactor; a desk has at most one terminal, so the count is the desk count. Revisit if hundreds of desks ever exist.

**Contract:** root [SPEC §6.5](../../SPEC.md#65-terminal-manager); this feature's [SPEC](SPEC.md) §3.

### R3-3 — Codex: one contained app-server, one remote TUI per session, delivery through `turn/start` behind an idle gate

**Decision:** The Codex control plane is `codex app-server --listen ws://127.0.0.1:<port> --ws-auth capability-token --ws-token-file <path>` on a port the daemon picks by binding and releasing, with a fresh token written 0600 under the data root at each start, spawned under the R2 containment primitive, recorded in `runtime/children.json`, started lazily before the first Codex session or delivery, and stopped only by Quit. The daemon holds one WebSocket JSON-RPC connection to it, authenticated with an `Authorization: Bearer <token>` header (`initialize` then `initialized`), and reads only the broadcasts `thread/started`, `thread/status/changed`, `thread/closed`, and `error`. A desk session is `codex --remote ws://127.0.0.1:<port> -C <workspace>` (new) or `codex resume <thread-id> --remote … -C <workspace>` (resume) in the desk's terminal, with `--remote-auth-token-env` naming an environment variable holding the same token. The bundled adapter is registered for the thread by a MarketRig-written `<workspace>/.codex/config.toml` (`[mcp_servers.marketrig]` `command`, `args`, `env`), not by `-c` overrides on the TUI command line: the thread lives in the app-server, which reads its own config (spike S). The thread pointer is the first non-`ephemeral` `thread/started` whose `thread.cwd` is the desk workspace after the launch; readiness is the first time that thread is `idle`, which the adapter tracks from `thread/started`'s own `thread.status` and every later `thread/status/changed`. Delivery is `turn/start` with `input: [{type: "text", text}]`, sent only when the thread's last broadcast status is `idle` and `thread/turns/list` shows no active turn at that instant; otherwise the prompt waits in the dispatcher until the next `idle` broadcast. The `turn/start` response is the handoff boundary: a `turn` in the result is `DELIVERED`; a JSON-RPC error is `FAILED` `DELIVERY_REFUSED`; a connection lost before the response is `FAILED` `HANDOFF_UNKNOWN`. Interrupt is `turn/interrupt` with the turn id read from `thread/turns/list` when asked, answered as the app-server answers. If the app-server process exits, the adapter ends every Codex terminal with `CONTROL_PLANE_LOST`, keeps every pointer, restarts the app-server once, and on a second failure marks the runtime `UNAVAILABLE` until `POST /runtimes/codex/retry`.

**Rationale:** The protocol's own words say `turn/start` "starts a new turn or joins an active turn", so the app-server offers no server-side queue MarketRig can rely on for "never interrupt a turn"; the idle gate is the adapter-private safe-delivery gating D36 names, and it is checked on demand the same way D69 reads the live turn. Observing broadcasts only keeps MarketRig unable to see or answer the desk's approvals (per D69).

On 2026-09-03, before the adapter was written, the launch and readiness questions were re-run on Codex 0.152.1. (S4, negative) The daemon cannot pre-create a thread for a new session: `thread/start {cwd}` succeeds, but `codex resume <that id> --remote …` exits with `thread/resume failed: no rollout found for thread id`, because a thread that has taken no turn has no rollout on disk — so a new session stays the plain `--remote` launch. (S5, positive) That launch needs no such trick: the TUI broadcasts a non-`ephemeral` `thread/started` about 0.3 s after spawn, before the operator types anything, carrying `cwd` = the workspace and `status: {type: "idle"}` inline; no `thread/status/changed` follows for at least 30 s. A resume of a thread that has taken a turn attaches cleanly and broadcasts `thread/status/changed` `notLoaded` then `idle`, and no `thread/started`. Hence the one readiness rule above, and the removal of the 60-second `thread/started` requirement for a resume. A `turn/start` MarketRig sends on its own connection reaches the attached TUI in both cases.

`ponytail:` Spike S ran on Codex 0.152.1 on 2026-09-03 and settled all three questions. (S1, negative) `-c mcp_servers.marketrig.*` on the `--remote` TUI command line does **not** reach the remote thread: `mcpServerStatus/list {threadId}` listed the user's global servers and no `marketrig`, because the thread lives in the app-server, which loads its own config — so the fallback replaces it, and MarketRig writes the registration into `<workspace>/.codex/config.toml`, which the same call then did list as `marketrig`. (S2, positive) a `turn/start` MarketRig's connection sends with `approvalPolicy: "untrusted"` routes its approval to the desk's TUI, not to MarketRig: the second connection saw only `thread/status/changed` to `active {activeFlags:["waitingOnApproval"]}` and `thread/name/updated`, never a `*/requestApproval`, and the prompt appeared on the TUI screen. (S3, positive) `--ws-auth capability-token` starts on a loopback listener when paired with `--ws-token-file <path>` (it exits 1 without it), MarketRig's client connects with an `Authorization: Bearer <token>` header, and the TUI accepts the same token through `--remote-auth-token-env <VAR>` — without the variable it exits with `environment variable ... is not set` — so the app-server is started with the token file and the local single-user boundary (§4.3) is no longer the only guard.

**Contract:** root [SPEC §6.3](../../SPEC.md#63-shared-control-planes), [§6.4](../../SPEC.md#64-runtime-adapter-contract), [§11](../../SPEC.md#11-daemon-prompt-delivery); this feature's [SPEC](SPEC.md) §4.

### R3-4 — Claude Code: per-launch files, three hooks, and the Channel bridge as a mode of `marketrig-mcp`

**Decision:** A Claude session is `claude --session-id <uuid>` (new, UUID minted by the daemon) or `claude --resume <uuid>` (resume), always with `--mcp-config <launch>/mcp.json --settings <launch>/settings.json --dangerously-load-development-channels server:marketrig-channel`, in the desk workspace. `<launch>` is `runtime/launch/<desk-id>/`, written 0600 before spawn and deleted at process end; `mcp.json` registers two stdio servers, `marketrig` (`marketrig-mcp --desk <id>`) and `marketrig-channel` (`marketrig-mcp --desk <id> --channel`); `settings.json` declares `SessionStart`, `Notification`, and `Stop` command hooks, each `marketrig --desk <id> session hook`. The bridge mode of `marketrig-mcp` declares `capabilities.experimental["claude/channel"] = {}` and no tools, discovers the daemon exactly as the CLI does, opens `GET /desks/{desk_id}/channel` as an authenticated WebSocket, and forwards each text frame — a JSON object `{content, prompt_id, kind}` — as one `notifications/claude/channel` with `content` = the frame's `content` and `meta` = `{prompt_id, kind}`; it owns no state and exits when either side closes. The desk's channel connection is delivery readiness; `SessionStart` with `source: startup | resume` is the pointer confirmation; `source: clear` repoints the desk to the new `session_id` with `SESSION_POINTER_CHANGED`. Delivery is one frame per prompt: a completed WebSocket write is `DELIVERED` (per D36), a write error or no channel connection at the attempt is `FAILED` (`CHANNEL_UNAVAILABLE`). No idle gate: Claude Code queues channel events itself and processes them in order at its next turn. `Stop` and `Notification` (`permission_prompt`, `idle_prompt`) are evidence only, as `SESSION_TURN_ENDED` and `SESSION_ATTENTION` events; Interrupt answers 409 `INTERRUPT_UNSUPPORTED` (per D69). A hook carrying a `session_id` that is not the desk's current pointer is recorded and ignored.

**Rationale:** D36 fixes the one-way Channel and the bridge; D53 says the bridge is a workspace binary, and `marketrig-mcp` already is one that speaks stdio MCP through `rmcp` and discovers the daemon — a second mode is one flag, not a second crate, and the two registrations stay distinct servers with distinct names so D4's split holds: the channel carries delivery, never a capability. Hooks are the only Claude event source (per D69) and the settings file is per launch so nothing MarketRig writes outlives the process.

`ponytail:` the development-channel flag prompts for a security confirmation the daemon cannot answer; the operator answers it in the attached terminal, and a dispatcher activation that stalls on it times out as delivery failure (R3-5). Replace `--dangerously-load-development-channels server:` with `--channels` the day Claude Code admits a non-plugin channel there.

**Contract:** root [SPEC §6.4](../../SPEC.md#64-runtime-adapter-contract), [§11](../../SPEC.md#11-daemon-prompt-delivery), [§13.2](../../SPEC.md#132-cli-continuity-plane); this feature's [SPEC](SPEC.md) §5.

### R3-5 — One dispatcher task per daemon; orientation and disclosure are prompt rows; activation failure fails what was queued

**Decision:** One tokio task wakes on a `Notify` signalled by every prompt insert and every adapter readiness or exit event, and on a 30-second recheck. For each desk with `QUEUED` prompts, oldest first: with a live ready session it asks the selected runtime's adapter to deliver the head prompt and moves it in one unit to `DELIVERED` or `FAILED` with the attempt's evidence; with a live session not yet ready it waits; with no live session it activates — resume when the selected runtime's pointer exists, otherwise start new — and on a new session inserts an `ORIENTATION` prompt ahead of the queue, plus one `DISCLOSURE` prompt when undisclosed `FAILED` prompts exist, each an ordinary row delivered by the same path. Readiness not reached within 120 seconds of spawn, or the process exiting before readiness, ends the activation: the process is ended with the reason the evidence supports, and every prompt `QUEUED` for that desk at that moment becomes `FAILED` with `ACTIVATION_FAILED` and the runtime's own failure in the attempt record. A dispatcher activation whose resume attempt exits before readiness starts new once, with `SESSION_POINTER_CHANGED` naming the old pointer as unresumable; explicit Continue never does. A prompt whose attempt began (`attempted_at_ns` set) but whose outcome was never written is resolved by recovery as `FAILED` `HANDOFF_UNKNOWN`.

**Rationale:** Root §7 and §11 already say what activation delivers and in what order; making orientation and disclosure rows keeps one delivery path, one evidence shape, and one FIFO. Failing what was queued at activation failure is root §7's "runtime-wide launch … failure fails daemon prompt delivery" applied literally, and it keeps later prompts free to try again.

**Contract:** root [SPEC §7](../../SPEC.md#7-activation), [§11.1](../../SPEC.md#111-states-and-ordering); this feature's [SPEC](SPEC.md) §6.

### R3-6 — Session controls are five routes under the desk; Switch decides then acts; one exit-reason vocabulary

**Decision:** `POST /desks/{desk_id}/session/activate` with `{"mode": "CONTINUE" | "NEW"}`, `/session/interrupt`, `/session/exit`, and `/session/switch` with `{"runtime": …}`, plus `GET /desks/{desk_id}/session` describing the live process or `null`. `CONTINUE` with no pointer answers 409 `NO_NATIVE_SESSION`; either mode with a live process answers 409 `SESSION_LIVE`; an `UNAVAILABLE` or `UNDISCOVERED` runtime answers 409 `RUNTIME_UNAVAILABLE`. Switch validates the target — a known runtime different from the current selection and `AVAILABLE` — before touching anything, then ends any live process with `INTERRUPTED`, moves `desks.selected_runtime` and appends `RUNTIME_SWITCHED` in one unit, and does not activate. Exit ends the process with `INTERRUPTED`. Every `agent_processes` row closes with `exit_reason IN ('EXITED','INTERRUPTED','QUIT','CONTROL_PLANE_LOST','DAEMON_LOST')` and one `SESSION_EXITED` event in the same unit. None of these routes exist in the CLI.

**Rationale:** This is D69 made concrete. Not activating on Switch keeps the route one decision with one effect; activation is its own route and the dispatcher's own path.

**Contract:** root [SPEC §6.2](../../SPEC.md#62-lifecycle-actions); this feature's [SPEC](SPEC.md) §7.

### R3-7 — Migration 4: pointers, processes, delivery states, runtimes, and the widened event vocabulary

**Decision:** Migration 4 adds `desks.selected_runtime` (`codex | claude`, default `codex`, settable at creation), `native_sessions (desk_id, runtime, native_session_id, updated_at_ns)` keyed by desk and runtime, `agent_processes` (one row per managed process with pid, native session, daemon UUID, `ready_at_ns`, `ended_at_ns`, `exit_reason`, `exit_code`), `runtimes` (R3-1), rebuilds `prompts` with `state IN ('QUEUED','DELIVERED','FAILED')`, kinds `ORIENTATION` and `DISCLOSURE`, and the attempt columns `attempted_at_ns`, `resolved_at_ns`, `runtime`, `native_session_id`, `failure_code`, `disclosed_at_ns`, and widens `operational_events.kind` with `RUNTIME_DISCOVERED`, `RUNTIME_UNAVAILABLE`, `CONTROL_PLANE_STARTED`, `CONTROL_PLANE_LOST`, `SESSION_STARTED`, `SESSION_READY`, `SESSION_POINTER_CHANGED`, `SESSION_ATTENTION`, `SESSION_TURN_ENDED`, `SESSION_INTERRUPTED`, `SESSION_EXITED`, `PROMPT_DELIVERED`, `PROMPT_FAILED`, and `RUNTIME_SWITCHED`. The recovery step closes every open `agent_processes` row of another daemon as `DAEMON_LOST`, fails every attempted-but-unresolved prompt as `HANDOFF_UNKNOWN`, and lists both under `sessions_lost` and `prompts_unknown` in the recovery event; the app-server child is handled by the R2 `children.json` step.

**Rationale:** Root §15 names exactly these durable facts and forbids a status machine; each column here is one of the listed facts and nothing else. Rebuilding `prompts` follows migration 3's pattern because SQLite cannot alter a `CHECK`.

**Contract:** root [SPEC §15](../../SPEC.md#15-persistence-crash-recovery-and-history); this feature's [SPEC](SPEC.md) §8.

### R3-8 — The gate drives the adapters against a harness-owned stand-in runtime that speaks the exact consumed protocol subset

**Decision:** `runtime-standin`, a second acceptance-only binary beside `trigger-code`, is registered as both runtimes' explicit executable in gate runs. Invoked as Codex it serves `app-server --listen ws://…` — `initialize`, `thread/start`, `thread/resume`, `thread/turns/list`, `turn/start`, `turn/interrupt`, and the four broadcasts — and as the TUI it connects to the remote endpoint, starts or resumes its thread, echoes every delivered input to its terminal, and scripts status changes; invoked as Claude it parses `--session-id`, `--resume`, `--mcp-config`, `--settings`, and the channel flag, spawns the configured stdio servers, runs the hooks from the settings file, and echoes each channel notification it receives from the bridge. Its behavior per launch is scripted through a control file the gate writes beside the workspace, so a scenario can order "stay active for 5 s after the first input", "exit before readiness", or "read the quotes resource through the registered adapter". Both stand-in halves live in the acceptance crate and share nothing with the daemon beyond the protocol.

**Rationale:** The real CLIs cannot run unattended — authentication, trust dialogs, and a model behind every turn — and the gate must be deterministic on both platforms (per D75). A stand-in at the protocol boundary is the same move as the stand-in feed and `trigger-code`, and it makes the adapters' wire contract executable evidence rather than prose.

**Contract:** root [SPEC §17](../../SPEC.md#17-verification); this feature's [SPEC](SPEC.md) §9.
