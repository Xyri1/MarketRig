# R4 — Memory, skills, and the closed loop: Feature Decisions

Local decisions for [Milestone R4](../../ROADMAP.md#milestone-r4--memory-skills-and-the-closed-loop), prefixed `R4-<n>`. They resolve mechanics the root SPEC defers (§16, §18) for R4's scope and contradict nothing settled; on merge they are summarized as one product `D<n>` in `sdd/DECISIONS.md`. Hindsight facts were verified on 2026-09-04 against `hindsight-api-slim[embedded-db]==0.9.2` installed from PyPI (the newest release; it resolved `pg0-embedded 0.15.1`) by reading its `config.py`, `main.py`, `api/http.py`, `pg0.py`, and `extensions/builtin/tenant.py`; the keyring 4 line was verified on crates.io the same day: `keyring 4.2.0` is a facade over `keyring-core 1.0.0` and per-platform store crates (`apple-native-keyring-store 1.0.2`, `windows-native-keyring-store 1.1.0`), and MarketRig pins the core and the two stores directly.

### R4-1 — The memory child is one installation row naming a launcher, started lazily under the containment primitive, restarted once

**Decision:** `memory_child` is one installation row: `executable_path`, `state` (`UNCONFIGURED | AVAILABLE | UNAVAILABLE`), `validated_at_ns`, and a failure code and message. The executable is Hindsight's own `hindsight-api` console script (`hindsight_api.main:main`) from an environment carrying the pinned wheel; R6's installer names the bundled one, and until then the operator names it through `POST /memory/discover {"executable": path}`. Discovery validates by running `<executable> --help` with a 10-second timeout and requiring `HINDSIGHT_API_PORT` in the output (the launcher prints each option's environment name); failures are `NOT_FOUND`, `CAPABILITY_MISSING`, `PROBE_FAILED`. At daemon start, step 6b re-validates an `AVAILABLE` row and is skipped under `MARKETRIG_TEST_DATA_ROOT`, like 6a. The child is started lazily by the first memory operation, or by the first operation after a loss, never by startup: bind `127.0.0.1:0`, take the port, release, spawn the launcher under the R2 containment primitive with cwd the data root and an environment composed only of the platform set §4.2 of the R3 feature SPEC lists plus Hindsight's own variables (§2.2 of this feature's SPEC), record it in `runtime/children.json`, and poll `GET /health` every 500 ms until it answers `200`, within 120 s. Readiness appends `MEMORY_STARTED {pid}`; the child exiting or the health poll failing appends `MEMORY_LOST` and the next operation starts it once more; a second loss without an intervening readiness sets the row `UNAVAILABLE` with `CHILD_FAILED` and the last line of the child's own output as the message, appends `MEMORY_UNAVAILABLE`, and holds until `POST /memory/retry`. The launcher writes its banner, its startup summary, and its `logging` records to **standard output** and leaves standard error empty, so the tail the daemon keeps is standard output. Quit stops the child after the terminals and the Codex app-server. The child's `HOME` (and `USERPROFILE`, `LOCALAPPDATA` on Windows) is `<data root>/hindsight/`, so pg0's instance directory lands under MarketRig's own root and, under the test seam, inside the evidence bundle.

**Rationale:** D65 fixes the child, the bearer, the disabled surfaces, and the one restart; D47 says the interpreter exists only for this child; D73 already reaps recorded children. A launcher path is the same shape as R3-1's runtime rows, and it is the smallest thing that lets the gate register a stand-in by explicit path, the operator run a uv environment before packaging exists, and R6 fill in the bundled path. Lazy start keeps D18's "never blocks daemon startup" literal — a pg0 cluster and a model verification take tens of seconds — and the `--help` probe is the only capability check that runs without a database or a key. Redirecting `HOME` is the one way to keep the embedded database inside the root D65's wrapper offers no data-directory setting for.

`ponytail:` the `--help` marker is the whole capability check (a `--version` if a later line adds one). pg0 honors `HOME`: verified on 2026-09-04 on macOS arm64 against the pinned wheel, a launcher whose `HOME` is a scratch directory put both its installation (`<HOME>/.pg0/installation/18.1.0`, 36 MB) and its instance (`<HOME>/.pg0/instances/marketrig/`, 48 MB) there and left the real `~/.pg0` byte-identical, and a second launcher under a second `HOME` took the next free PostgreSQL port (5433) rather than colliding on 5432 — so a data root is self-contained and two roots can run at once. Redirecting `HOME` also relocates the child's caches, which is why the whole `<data root>/hindsight/` tree, not just `.pg0`, is MarketRig's to delete with the root.

**Contract:** root [SPEC §4.4](../../SPEC.md#44-configuration-scopes), [§4.6](../../SPEC.md#46-daemon-startup-and-shutdown), [§16](../../SPEC.md#16-memory-and-skills); this feature's [SPEC](SPEC.md) §2.

### R4-2 — Provider settings are one row plus one credential-store entry; the model list is fetched live; the embedding model locks on the first retain

**Decision:** `memory_provider` is one installation row: `base_url`, `llm_model`, `embedding_model`, `key_ref`, `embedding_locked_at_ns`, `updated_at_ns`. `PUT /memory/provider {base_url, api_key?, llm_model, embedding_model}` validates the URL (`http` or `https`, no credentials, no query), stores the key through `keyring-core =1.0.0` with the platform store crate named explicitly (`apple-native-keyring-store =1.0.2` on macOS, `windows-native-keyring-store =1.1.0` on Windows, set as the default store at daemon start) under service `marketrig` and account `hindsight-provider`, keeps `key_ref` as the opaque marker that a key exists, appends `MEMORY_CONFIGURED {base_url, llm_model, embedding_model}`, and restarts a running child so the new environment applies. `api_key` omitted keeps the stored key; a credential-store failure answers `CREDENTIAL_STORE_UNAVAILABLE` and writes nothing. `GET /memory` answers the row with `api_key_present` and never the key. `GET /memory/provider/models` fetches `<base_url>/models` with the stored key at request time, answers the provider's `data[].id` list, and fails `PROVIDER_UNREACHABLE` with the HTTP status or transport error — nothing is persisted or cached. The first successful retain stamps `embedding_locked_at_ns`; after that a `PUT` whose `embedding_model` differs answers `409 EMBEDDING_MODEL_LOCKED`. Under `MARKETRIG_TEST_DATA_ROOT` the credential store is the file `runtime/credentials.json` (0600) inside the relocated root instead of the platform store.

**Rationale:** D18 fixes every clause: one endpoint and key for both models, no reranker, a live never-cached list, an explicit fetch failure, and the lock. D49 fixes the store and the one environment exception. The lock is stamped on the first retain rather than on child readiness because that is the first moment Hindsight has initialized data with the embedding model. The seam file exists because the gate must never touch the per-user root (§17) and the keychain is per-user state; it is the harness seam, not a fallback on native-store failure, which stays refused.

`ponytail:` one provider, one key, one row. A second provider for embeddings, or a reranker, is a column set behind the same `PUT` if D18 ever changes.

**Contract:** root [SPEC §4.4](../../SPEC.md#44-configuration-scopes), [§17](../../SPEC.md#17-verification); this feature's [SPEC](SPEC.md) §3.

### R4-3 — Banks are derived, the four memory operations are synchronous pass-throughs with attribution metadata, and MarketRig stores nothing but the event

**Decision:** A desk's bank is `desk-<uuid without hyphens>`; nothing outside `marketrigd` ever sees or supplies it, and it is provisioned by Hindsight itself on the first write (0.9.2 auto-creates a bank on retain, recall, and reflect). `GET /desks/{d}/memory` answers the desk-scoped status. `POST /desks/{d}/memory/retain {content, context?, tags?}` calls `POST /v1/default/banks/<bank>/memories` with one item, synchronous (`async: false`), `metadata = {source: INTERACTIVE|TRIGGER, desk_id, trigger_id?, firing_id?}` from the request's attribution headers, the agent's `context` and `tags` verbatim, and no timestamp (Hindsight stamps now); it answers `{items_count}` and appends `MEMORY_RETAINED {source, trigger_id, firing_id, items_count, tags}`. `POST /desks/{d}/memory/recall {query, budget?, tags?}` calls `.../memories/recall` and answers `results[]` as `{id, text, type, context, tags, metadata, occurred_start, mentioned_at}`; `POST /desks/{d}/memory/reflect {query, budget?}` calls `.../reflect` and answers `{text, based_on: [{id, text, type}]}`; both append `MEMORY_RECALLED {op, results}`. Limits: `content` ≤ 64 KiB, `context` ≤ 4 KiB, `query` ≤ 8 KiB, ≤ 16 tags of ≤ 64 characters; `budget IN ('low','mid','high')`, default `mid`. Every call carries `Authorization: Bearer <per-start bearer>`; timeouts are 180 s for retain and reflect and 60 s for recall. Errors: `MEMORY_UNCONFIGURED` (no launcher or no provider), `MEMORY_UNAVAILABLE` (child `UNAVAILABLE`, or not ready within the start window), `MEMORY_REJECTED` (a Hindsight 4xx, its `detail` as the message), `MEMORY_TIMEOUT`, `MEMORY_ERROR` (a 5xx or transport failure). The CLI group is `marketrig [--json] memory <status|retain|recall|reflect> <desk-name-or-id> …` with `retain --content <text> | --file <path>`, `--context`, `--tag` (repeatable), and `recall`/`reflect --query <text>`, `--budget`, `--tag`.

**Rationale:** D16 and D65 fix the four capabilities, the derived bank, and the absence of a content store; D17 keeps the choice of what to retain with the agent. Attribution in `metadata` reuses the two headers R2 already sends and lets a later recall tell an interactive lesson from a trigger's. Synchronous retain is the only shape that lets the agent, and the gate, know the lesson landed before the session ends. Answering a fixed subset of Hindsight's result fields keeps its API from becoming product contract (root §3).

`ponytail:` one item per retain and no batch, no `document_id`, no entities, no temporal window, no `types` filter. Each is a request field behind the same route if evaluation evidence shows the agent needs it.

**Contract:** root [SPEC §13.2](../../SPEC.md#132-cli-continuity-plane), [§16](../../SPEC.md#16-memory-and-skills); this feature's [SPEC](SPEC.md) §4.

### R4-4 — The constitution, the improvement skill, and the skills link are seeded at creation; only the link is reconciled afterwards

**Decision:** Desk creation's bootstrap writes `AGENTS.md` with the constitution §5.1 of this feature's SPEC prints, `.agents/skills/desk-improvement/SKILL.md` with the improvement skill §5.2 prints, and the `.claude/skills` link — a relative symlink to `../.agents/skills` on macOS, a directory junction to the absolute `.agents/skills` on Windows — each step skipped when its target already exists, so the sequence stays idempotent and a retried creation completes without rewriting. After `READY`, startup validation reconciles the shim and the link only: a missing `.claude/skills` is recreated (creating an empty `.agents/skills/` first if it is missing), a link pointing elsewhere is repointed, and an ordinary directory or file at `.claude/skills` is left alone and reported in the derived workspace status reason. `AGENTS.md`, the seeded skill, and every other file are never touched again; a desk created before R4 keeps its placeholder constitution and gains only the link and the empty tree. The seeded texts are English, byte-identical under both locales, and name every surface R1–R4 give the agent, including the equity simulation's limits (per D78).

**Rationale:** D20 fixes creation ordering and the never-rewrite rule, D21 the one physical tree and the link's two forms, D22 the always-loaded loop and the seeded on-demand skill; root §5.2 already lists the three artifacts. Reconciling the link is what root §5.1 names as MarketRig's own material. Leaving a pre-R4 desk's constitution alone is the never-rewrite rule applied to MarketRig's own change of mind.

`ponytail:` the constitution is one file and one wording. A per-market or per-runtime variant is a template the day one is needed.

**Contract:** root [SPEC §5.1](../../SPEC.md#51-workspace-ownership), [§5.2](../../SPEC.md#52-creation-and-recovery), [§16](../../SPEC.md#16-memory-and-skills), [§18](../../SPEC.md#18-implementation-deferred-contracts); this feature's [SPEC](SPEC.md) §5.

### R4-5 — Migration 5: two settings rows and six event kinds; recovery needs no new step

**Decision:** Migration 5 adds `memory_child` and `memory_provider` (one row each, `id = 1`), and widens `operational_events.kind` with `MEMORY_CONFIGURED`, `MEMORY_STARTED`, `MEMORY_LOST`, `MEMORY_UNAVAILABLE`, `MEMORY_RETAINED`, and `MEMORY_RECALLED` by the migration-2 rebuild pattern. The child's live state (`NOT_STARTED | STARTING | READY | LOST`) and its pid are held in memory and reported by the status routes; no process row exists for it. Recovery adds no step: the Hindsight child is a `children.json` record like the app-server, so the existing first step reaps it on macOS and discards its record on Windows.

**Rationale:** Root §15 names the durable facts and forbids a status machine; the two rows are configuration, the events are evidence, and the child's liveness is a fact the next start re-derives by reaping. D73 was written with this child in mind.

**Contract:** root [SPEC §15](../../SPEC.md#15-persistence-crash-recovery-and-history); this feature's [SPEC](SPEC.md) §6.

### R4-6 — The gate runs a stand-in memory child and performs the agent's steps through the CLI; the experiment attends real Hindsight

**Decision:** `memory-standin`, a third acceptance-only binary beside `trigger-code` and `runtime-standin`, is registered as the memory launcher in gate runs. It honors `HINDSIGHT_API_HOST`, `HINDSIGHT_API_PORT`, and `HINDSIGHT_API_TENANT_API_KEY`, answers `--help` with the marker, serves `/health`, retain, recall, and reflect on the exact paths and field names the daemon consumes with an in-memory per-bank store, substring recall, and reflect as a concatenation of matches, refuses a wrong bearer `401`, and reads its knobs from the `memory` object of the one `MARKETRIG_STANDIN_SCRIPT` file — `health_after_ms`, `exit_after_ms`, `reject_retain`; invoked as `memory-standin --models <port>` it serves only `GET /v1/models` with a scripted list, which is the gate's provider stand-in. Gate scenarios G33–G37 extend the chain after G32: configuration and secrets, two-desk isolation, the closed loop, the later session, and Hindsight stopped. In G35 and G36 the harness itself performs the agent's steps — `marketrig memory retain` from the desk workspace and a skill file written under `.agents/skills/` — after the `EVALUATION` prompt is observed as the stand-in session's input, because those steps are agent-owned and the gate must prove only that the harness makes them possible and durable. E5 is the attended scenario per cell: the harness configures real Hindsight from `MARKETRIG_EXPERIMENT_HINDSIGHT` (the launcher) and `MARKETRIG_EXPERIMENT_MEMORY_{BASE_URL,API_KEY,LLM_MODEL,EMBEDDING_MODEL}` on its own environment, skips with evidence when any is unset, and drives one round trip, the evaluation, the retain, the skill edit, and a later session's recall, with the agent-owned steps ending inconclusive.

**Rationale:** D75 fixes the fake memory child, and a stand-in at the HTTP boundary is the same move as the stand-in feed and the stand-in runtime. Letting the harness play the agent through public surfaces only (per D67) proves the mechanics without a model and without MarketRig deciding what should be learned; the runtime stand-in gains no scripting for it. The experiment's provider comes from the operator's environment because the key must reach the daemon somehow and the harness process is the operator's own.

**Contract:** root [SPEC §17](../../SPEC.md#17-verification); this feature's [SPEC](SPEC.md) §7.
