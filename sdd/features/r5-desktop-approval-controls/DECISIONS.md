### R5-1 — Policies are one installation row behind one resource; a policy change decides nothing

**Decision:** Migration 6 creates `installation_settings` as one row (`id = 1`) with `trigger_code_policy` (`ALWAYS_ALLOW | REQUIRE_APPROVAL`, default `REQUIRE_APPROVAL`), `paper_order_policy` (same vocabulary, default `ALWAYS_ALLOW`), `delivery_mode` (`CHECK (delivery_mode = 'QUEUE')`), and `updated_at_ns`. `GET /settings/policies` answers the three columns plus `steer_available: false`; `PUT /settings/policies` takes any subset of the three, refuses `delivery_mode: "STEER"` as `409 STEER_DISABLED` and any other unknown value as `400 VALIDATION`, writes the row and one installation-wide `POLICY_CHANGED {field, from, to}` per field that actually changes, in one unit, and answers the resource. The unit that creates a code snapshot or accepts an order reads its policy column in the same transaction, with no cache. A policy change affects only snapshots and actions created after it: a `PENDING` record stays pending under **Always allow** until decided, and an `ALWAYS_ALLOW` record is never re-gated.

**Rationale:** D70 fixes the three columns, the defaults, the resource, the refused `STEER`, and the per-field record; `installation_settings` did not exist before R5 because R4 kept its two settings in topic-named rows, and one row for the three policies is the same shape. Reading the column inside the unit is what keeps the policy honest under a concurrent `PUT`. Leaving pending records alone on a policy change keeps every decision a person's, which is the reason the boundary exists.

**Contract:** root [SPEC §4.4](../../SPEC.md#44-configuration-scopes), [§11.2](../../SPEC.md#112-queueing-and-reserved-steering); this feature's [SPEC](SPEC.md) §2.

### R5-2 — Approval is one vocabulary on two existing rows, one listing, and one decision route

**Decision:** `code_snapshots` and `trading_actions` each gain `approval` (`ALWAYS_ALLOW | PENDING | APPROVED | DENIED`) and `decided_at_ns`, null exactly while `PENDING`; migration 6 rebuilds both, backfilling `ALWAYS_ALLOW` with `decided_at_ns = created_at_ns` and dropping `code_snapshots.approved_at_ns`, which the Trigger resource keeps deriving (`decided_at_ns` when the snapshot is `ALWAYS_ALLOW` or `APPROVED`, absent otherwise). There is no approvals table (per D70). `GET /approvals?state=PENDING|DECIDED|ALL` lists both kinds installation-wide, newest first, each item `{kind: TRIGGER_CODE | PAPER_ORDER, id, desk_id, desk_name, approval, requested_at_ns, decided_at_ns, detail}` where `id` is the snapshot id or the trading action's `id` (both UUIDv7, both unique) and `detail` is the snapshot without `source` or the action's request; `GET /approvals/{id}` adds the snapshot's `source`. `POST /desks/{d}/approvals/{id} {"decision": "APPROVE" | "DENY"}` resolves `id` against both tables under that desk, answers `404 APPROVAL_NOT_FOUND` or `409 APPROVAL_DECIDED`, and otherwise applies R5-3 or R5-4 and appends `APPROVAL_DECIDED {kind, id, decision}`. Requests append `APPROVAL_REQUESTED {kind, id, …}` in the unit that creates the pending record. No `marketrig` command reads or writes any of it; the agent sees `approval` on the records it already reads.

**Rationale:** D70 says the approval *is* the snapshot row or the action row, so the vocabulary belongs on those rows and the listing is a union query, not a table. One decision route with one body is the smallest surface the desktop and the smoke need, and resolving by id under the desk keeps every write desk-scoped. D70 names the pending order's state `PENDING_APPROVAL` and the denial `failure_code = DENIED`; this decision realizes them as `approval = PENDING` on the row and `DENIED` in the stored outcome, one vocabulary for both kinds — the merge refreshes D70's wording.

`ponytail:` two kinds, one route, resolved by trying both tables. A third approvable thing is a third arm of the same match.

**Contract:** root [SPEC §12.3](../../SPEC.md#123-trading-actions-and-approvals), [§15](../../SPEC.md#15-persistence-crash-recovery-and-history), [§18](../../SPEC.md#18-implementation-deferred-contracts); this feature's [SPEC](SPEC.md) §3.

### R5-3 — A pending snapshot is a null projection; approval recomputes it; denial is a snapshot the trigger keeps

**Decision:** Trigger creation and a code-changing patch under `REQUIRE_APPROVAL` insert the snapshot `PENDING` and write `next_occurrence_ns = NULL`; the projection rule becomes *non-null only when the trigger is enabled, undeleted, and its snapshot is null, `ALWAYS_ALLOW`, or `APPROVED`*, applied wherever the projection is computed today (create, patch, enable, disable, the scheduler's advance). A patch whose code fingerprints identical to the current snapshot keeps that snapshot and its state (per root §8.3, only a change requires reapproval). `APPROVE` sets `APPROVED`, stamps `decided_at_ns`, recomputes the projection from now — a recurring trigger gets its next future occurrence, an elapsed one-off stays `NULL` — and signals the scheduler, in one unit. `DENY` sets `DENIED`; the trigger keeps referencing the denied snapshot, stays undue forever, and is freed only by a patch that attaches different code or detaches code. The Trigger resource's `code` object gains `approval` and `decided_at_ns`, and `marketrig trigger show` prints them.

**Rationale:** D70 folds eligibility into `next_occurrence_ns` so the scheduler's one query needs no join and enable or disable cannot resurrect an unapproved trigger; recomputing from the decision instant is what keeps an approved elapsed one-off undue, as §8.3 requires. Keeping the denied snapshot on the trigger is the record: deleting it would erase what the user refused.

**Contract:** root [SPEC §8.3](../../SPEC.md#83-trigger-lifecycle), [§10](../../SPEC.md#10-scheduled-trigger-semantics); this feature's [SPEC](SPEC.md) §3.2.

### R5-4 — A pending order is a validated action row the sandbox has not seen; approval re-enters acceptance; cancel is ungated and names the state

**Decision:** Under `REQUIRE_APPROVAL`, `submit` validates form (`ORDER_INVALID`), attribution (`ATTRIBUTION_INVALID`), and desk readiness (`DESK_NOT_READY`) exactly as today, then inserts the `trading_actions` row with `approval = PENDING`, `outcome = NULL`, appends `APPROVAL_REQUESTED`, and answers `202` with the ActionRecord — `approval: "PENDING"` and no `outcome` — without starting or touching the node; a repeated `action_id` answers `200` with that record. `APPROVE` requires the desk's node `RUNNING` (started lazily as every live route does; `503 MARKET_UNAVAILABLE` leaves the row pending), then runs the ordinary accept path from the point acceptance left it — the stored request, `client_order_id = action_id` — and lands the outcome on the row as any order does, including a sandbox refusal; `DENY` writes `approval = DENIED`, `outcome = {"failure_code": "DENIED"}`, and the record is terminal. `CANCEL` is never gated; a cancel naming an order whose submit is still `PENDING` answers `409 ORDER_PENDING_APPROVAL` and changes nothing, because there is no sandbox order to cancel and the agent cannot decide the approval. The policy applies equally to `SESSION` and `TRIGGER` sources. `GET /desks/{d}/history/actions` and `marketrig history actions <desk>` list the desk's trading actions newest first with `approval` and `decided_at_ns`, which is how an agent learns why its order has not filled. The MCP `submit_order` tool returns the same record, so a pending order is visible in the tool result. The seeded constitution gains one paragraph naming the boundary for desks created from R5 on; existing desks are never rewritten (per D20).

**Rationale:** D70 fixes every clause — pending commits without enqueueing, answers a null projection, replays idempotently, approval re-enters acceptance where it left off, denial is terminal, cancel is ungated, a decision queues no prompt. Validating form before pending means the user never sees a request the daemon would have refused anyway. A distinct cancel code, rather than `ORDER_NOT_FOUND`, is the honest answer to an order the agent did submit. The actions listing is the read D70 grants — visibility is not a crossing.

`ponytail:` the withheld request is replayed from the stored JSON; no queue, no worker, no timer. A pending order the user never decides stays pending forever, and expiry is a column if evidence asks for it.

**Contract:** root [SPEC §12.3](../../SPEC.md#123-trading-actions-and-approvals), [§13.1](../../SPEC.md#131-mcp-trading-plane), [§13.2](../../SPEC.md#132-cli-continuity-plane); this feature's [SPEC](SPEC.md) §3.3.

### R5-5 — The events tail is one publisher over a post-commit signal; browser sockets authenticate in their first frame behind an exact-origin allowlist

**Decision:** The store gains one post-commit signal (a `tokio::sync::Notify` pulsed by the database thread after every committed unit). One publisher task holds the installation's `(occurred_at_ns, id)` cursor, wakes on the signal or every 5 s, reads the rows after its cursor in pages of 500, and fans each row out to every subscriber's bounded 1 000-frame queue; a full queue closes that subscriber `4408`. `WS /events` upgrades, then requires one text frame within 5 s — `{"bearer": "<credential>", "after": "<occurred_at_ns>:<id>"?}` — closing `4401` otherwise; it subscribes before it reads, replays from the table after `after` up to the tail position at subscription, answers `{"tail": "<cursor>"}`, then streams `{id, kind, desk_id, occurred_at_ns, payload}` per row; an `after` no row matches is ignored and the tail reported. `GET /events?desk_id=&before=<cursor>&limit=≤500` lists newest first with `next_before`; `marketrig desk events <desk> [--limit n]` is its agent-facing form. Every WebSocket route — `/events`, the terminal, the Claude channel — checks the `Origin` header at the handshake when one is present: exactly `tauri://localhost`, `http://tauri.localhost`, or `http://localhost:1420` (Tauri's macOS, Windows, and Vite dev origins, verified 2026-09-04), else `403 ORIGIN_REFUSED` before the upgrade; a request with no `Origin` (the CLI, the bridge, the harness) passes. The terminal socket keeps its header path and gains the same first-frame path when no `Authorization` header is present, after which its pre-attachment checks answer as close codes — `4404` desk not found, `4409` no live session — instead of HTTP statuses; the channel socket stays header-only, because only the bridge opens it. The desktop learns of a session starting on a desk through the events socket and attaches then, which is how D66's *attach to the desk* intent is met without changing R3's socket.

**Rationale:** D71 fixes the tail, the client-held cursor, the gapless boundary, the bounded queue, and the listing; the post-commit signal is the one thing the store lacks. D66 fixes first-frame authentication and the origin allowlist because the browser WebSocket API cannot send headers and D44 forbids credentials in URLs; keeping the header path means the CLI and the harness change nothing. Close codes after the upgrade are the only way to tell an unauthenticated browser why, since the browser hides handshake statuses from script.

**Contract:** root [SPEC §4.3](../../SPEC.md#43-local-single-user-boundary), [§6.5](../../SPEC.md#65-terminal-manager), [§14](../../SPEC.md#14-desktop-and-application-lifecycle), [§15](../../SPEC.md#15-persistence-crash-recovery-and-history); this feature's [SPEC](SPEC.md) §4.

### R5-6 — The shell is one Tauri crate with four commands, three sidecars, and no HTTP

**Decision:** `src-tauri/` is the workspace crate `marketrig-desktop` on `tauri =2.11.5`, `tauri-build =2.6.3`, `tauri-plugin-single-instance =2.4.4`, `tauri-plugin-notification =2.4.0`, `tauri-plugin-autostart =2.5.1`, and `tauri-plugin-log =2.9.1`, with `marketrigd`, `marketrig`, and `marketrig-mcp` declared as `bundle.externalBin` sidecars so they land beside the application binary on both platforms. Its commands are `read_endpoint` (the parsed `runtime/endpoint.json` or `null`), `start_daemon` (spawns the sidecar `marketrigd` detached — its own session on macOS, no Job Object on Windows — and returns once the endpoint file is rewritten with a new daemon UUID, within 30 s), `exit_app`, and `set_tray_pending(n)`; R6 adds `set_locale`. The webview verifies the daemon itself through authenticated health and the UUID match, and calls `start_daemon` only when that fails; the shell never performs an HTTP request and holds no state but the tray. The window's `CloseRequested` is prevented and the window hidden; the tray menu is *Open MarketRig*, a disabled *n pending approvals* line, and *Quit MarketRig*; left-clicking the tray icon shows and focuses the window; the single-instance callback does the same. Quit is the webview's `POST /quit`, a wait of up to 10 s for health to stop answering, then `exit_app`; the tray's Quit asks the webview to run that sequence through a Tauri event. Autostart is offered in Settings, default on, and launches the app with `--hidden`, which starts to the tray. Notifications are sent by the webview through the plugin binding for the event kinds §6.4 of this feature's SPEC lists, only while the window is hidden or unfocused. The shell writes its own bounded log through the log plugin's `LogDir` target.

**Rationale:** D66 fixes the command set and the HTTP-free rule; D26 close-hides and Quit; D52 the two plugins; D30 Tauri 2. Sidecars are the packaging shape Tauri already has for exactly this, and resolving the daemon beside the binary is what lets the packaged smoke run from a wiped root with no installer work. Verifying in the webview keeps one verifier (root §4.3).

`ponytail:` the tray count is a menu line and a title, not a badge; a dock badge on macOS is one call behind the same command if wanted.

**Contract:** root [SPEC §4.6](../../SPEC.md#46-daemon-startup-and-shutdown), [§14](../../SPEC.md#14-desktop-and-application-lifecycle); this feature's [SPEC](SPEC.md) §5.

### R5-7 — The frontend is generated types, four composables, three panels, and one token block

**Decision:** The root frontend pins `vue =3.5.42`, `vite =8.2.2`, `@vitejs/plugin-vue =6.0.8`, `typescript =6.0.3`, `tailwindcss` and `@tailwindcss/vite =4.3.3`, `reka-ui =2.10.4`, `vue-i18n =11.4.10` (`legacy: false`), `ghostty-web =0.4.0`, `@tauri-apps/api =2.11.1`, `@tauri-apps/cli =2.11.4`, the three plugin bindings, `@hey-api/openapi-ts =0.99.0`, and the check set of R5-8, on Node.js `24.18.0` and `pnpm =11.25.0` through Corepack. The REST client is generated from `marketrigd --openapi`, the document `utoipa =5.5.0` and `utoipa-axum =0.2.0` emit from the daemon's own route definitions, with the Fetch client as the bundled `@hey-api/client-fetch` plugin of `openapi-ts` — the separate `@hey-api/client-fetch` package D59 names has been bundled into `openapi-ts` since its 0.73.0 and is deprecated on npm, so it is not installed. Four composables carry all shared state: `useDaemon` (endpoint, bearer in memory, health, the generated client's configuration), `useEvents` (the one `WS /events` connection, its cursor, and refetch handlers), `useTerminal` (one warm ghostty-web `Terminal` and one terminal socket per live desk, kept across desk selection and window hiding), and `useApprovals` (the pending listing and the tray count). Everything else is component-local. The layout is three panels — a 240 px desk list, the terminal well, a 360 px right panel collapsible to a rail — with Reka UI `Tabs` for the right panel (*Desk*, *Triggers*, *Approvals*, *Activity*, *Settings*), `Select` for enumerated settings, and `AlertDialog` for Deny and Quit. The visual system is the one `@theme` block §6.5 prints, with colour reserved for the five state roles plus one accent, a 2 px status gutter on every desk row and the terminal well's edge, a dark terminal well in both schemes, and two font stacks split by provenance. Every string a person reads goes through `t()` from an `en` catalog, so R6 adds a file rather than a mechanism; every machine token — ids, codes, decimal text, instrument ids — is rendered verbatim in the terminal stack.

**Rationale:** D55–D59 and D62 fix the stack and the state model; D72 the token set and the refetch rule; D68 the catalog discipline. The bundled client is a pin fact, not a decision change: the generated code and the `setConfig` surface are the ones D59 chose. Four composables is the smallest count that keeps one connection per socket kind and one warm presentation per desk without a store.

**Contract:** root [SPEC §4.3](../../SPEC.md#43-local-single-user-boundary), [§14](../../SPEC.md#14-desktop-and-application-lifecycle); this feature's [SPEC](SPEC.md) §6.

### R5-8 — Verification is the OpenAPI drift check, four gate scenarios, the frontend's checks, and an embedded-driver packaged smoke

**Decision:** CI adds a `frontend` job on both platforms: Corepack-provisioned pnpm, `pnpm install --frozen-lockfile`, `cargo run -p marketrigd -- --openapi > openapi.json`, `pnpm generate`, `git diff --exit-code src/client`, then Prettier, ESLint, `vue-tsc`, and Vitest (`@vue/test-utils =2.5.0`, `jsdom =30.0.1`, `vitest =5.0.0`, `vue-tsc =3.3.11`, `eslint =10.10.0`, `prettier =3.9.6`). Gate scenarios G38–G41 extend the chain after G37 — policies and the events tail, trigger-code approval, paper-order approval, and socket authentication with a hard kill — and G21 gains a prologue setting `trigger_code_policy` to `ALWAYS_ALLOW`, as does the experiment's E3 setup, because the daemon now defaults to **Require approval** (per D70). The packaged smoke is `pnpm smoke`: WebdriverIO `@wdio/cli =9.31.5` with `@wdio/tauri-service =1.3.0` in `driverProvider: 'embedded'` mode on both platforms (macOS has no WKWebView WebDriver; the embedded server is the documented path), against the bundled application, run only when `MARKETRIG_SMOKE_WIPE=1` — the one flag under which it deletes the real per-user data root, log root, and `~/.marketrig` before launching. It registers `runtime-standin` by explicit path through the Settings tab so a terminal can attach, and drives the REST routes with the bearer it reads from the real endpoint file for the agent-side steps. No new attended experiment scenario: R5's evidence is mechanical.

**Rationale:** D59 requires the drift check; D60 and D61 fix the tools; D75 the gate's growth by scenario. The smoke is the one leg that touches the per-user root (root §17), so it must wipe it deliberately and never by default. Embedded mode is the only one that runs on both platforms.

**Contract:** root [SPEC §17](../../SPEC.md#17-verification); this feature's [SPEC](SPEC.md) §7, §8.
