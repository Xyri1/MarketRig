# R2 — Scheduled triggers: Feature Decisions

Local decisions for [Milestone R2](../../ROADMAP.md#milestone-r2--scheduled-triggers), prefixed `R2-<n>`. They resolve mechanics the root SPEC defers (§18) for R2's scope and contradict nothing settled; on merge they are summarized as one product `D<n>` in `sdd/DECISIONS.md`.

### R2-1 — Recurrence is computed on the wall clock and resolved through the zone, candidate by candidate

**Decision:** A one-off stores its absolute UTC instant `at_ns`. A recurring schedule stores one RRULE value (the text after `RRULE:`, no prefix), a naive local `dtstart` (`YYYY-MM-DDTHH:MM:SS`), and an IANA `tz`. Candidates come from `rrule =0.14.0` iterating in a fixed UTC frame over the naive wall-clock values — so the rule's `BYHOUR`, `BYDAY`, and interval arithmetic are the local-time arithmetic RFC 5545 describes — and each candidate's wall clock is then resolved through `chrono-tz =0.10.4` in the named zone: a wall-clock value that does not exist there (a spring-forward gap) is skipped, and one that exists twice (a fall-back overlap) takes its earlier instant. The daemon never lets the recurrence crate resolve zones itself. Form rejections are decided at creation and reschedule, answering `TRIGGER_INVALID`: `FREQ=SECONDLY`, `COUNT`, `UNTIL`, `BYSECOND`, any line break or `RRULE:`, `DTSTART`, `RDATE`, `EXDATE`, `EXRULE` token in the rule text, an unparseable rule, an unknown zone, an unparseable `dtstart`, and a one-off `at` that is not in the future. The next-occurrence projection is always the first candidate strictly after a reference instant, recomputed from the definition's own anchor: after acceptance the reference is the accepted occurrence; after a miss, enable, reschedule, or creation it is now.

**Rationale:** The root contract (per D37, D40) fixes the DST behavior in words; resolving each candidate through `from_local_datetime` makes those words the literal code path, independent of whatever the recurrence crate does with zones in its own iterator. Rejecting `BYSECOND` with `SECONDLY` is what "sub-minute recurrence" means once a rule can carry multiple second values. A one-off in the past would be an instant miss by construction, so refusing it keeps miss evidence meaningful.

`ponytail:` every projection iterates from the anchor rather than from a stored cursor; at daily and hourly cadences that is a few hundred candidates a year. The upgrade path is a persisted iteration cursor if minutely rules with old anchors ever show in the scheduler's timing.

**Contract:** root [SPEC §10](../../SPEC.md#10-scheduled-trigger-semantics); this feature's [SPEC](SPEC.md) §2.

### R2-2 — One scheduler task, one acceptance unit, one miss record per range

**Decision:** One tokio task in `marketrigd` waits on the earliest eligible `next_occurrence_ns`, a 60-second recheck, or a `Notify` that every trigger mutation signals, then runs **one** `BEGIN IMMEDIATE` unit over every due trigger — enabled, undeleted, with a non-null projection at or before now. A due trigger whose occurrence is at or after this daemon's `started_at_ns` and no more than 60 seconds old is **accepted**: the unit inserts the firing row (occurrence identity, brief, context, revision, snapshot identity), inserts the `TRIGGER_RESULT` prompt when the firing carries no code, and consumes a one-off (projection `NULL`) or advances a recurring definition to the first candidate after the occurrence. Any other due trigger is **missed**: the unit appends one `TRIGGER_MISSED` operational event summarizing the range from the stale projection through now with the candidate count (capped at 10,000 and reported as such), and the one-off becomes terminal (`NULL`) while the recurring definition advances to the first candidate after now. Disabled, deleted, and consumed definitions carry a `NULL` projection, so the partial index the task reads never sees them and no miss accrues while disabled. `firings UNIQUE (desk_id, trigger_id, occurrence_ns)` is the duplicate guard: a second wake for the same occurrence violates it and creates nothing.

**Rationale:** D40 asks for durable projections plus an in-memory wake and no framework; one task and one unit are the whole of that. The daemon-start rule makes downtime misses fall out of the same comparison as lateness, so startup needs no special reconciliation pass — the first pass after start is it.

**Contract:** root [SPEC §10](../../SPEC.md#10-scheduled-trigger-semantics); this feature's [SPEC](SPEC.md) §3.

### R2-3 — Code snapshots are fingerprinted rows; execution is one primitive over `process-wrap`

**Decision:** A snapshot row holds the UTF-8 `source` (at most 256 KiB), a `suffix` (empty, or `.` followed by 1–15 alphanumerics), the `argv` (1–64 strings, each at most 4 KiB, exactly one of them the whole argument `{script}`), `timeout_secs` (1–3600, default 300), and the lowercase-hex SHA-256 over `source`, `suffix`, the argv JSON, and the timeout, computed with `ring =0.17.14` (already in the workspace graph under rustls). Under R2's fixed **Always allow**, `approved_at_ns` equals `created_at_ns` on every snapshot. A firing that carries a snapshot is executed by writing the source to `<data root>/runtime/scripts/<firing_id><suffix>` (mode `0700` on macOS), substituting that absolute path for the placeholder, and spawning the argv directly — no shell — with the desk workspace as the working directory, the daemon's environment plus `MARKETRIG_DESK_ID`, `MARKETRIG_DESK_NAME`, `MARKETRIG_TRIGGER_ID`, and `MARKETRIG_FIRING_ID`, the version-1 firing document on standard input followed by EOF, and standard output and error captured concurrently under caps of 1 MiB and 256 KiB. The containment primitive is `process-wrap =9.1.0` — `ProcessSession` (a `setsid` session and group) on macOS, `JobObject` with kill-on-close on Windows — whose `kill` ends the whole group; it is the one spawn-and-terminate path every managed child MarketRig owns from here on (per D41, D73). Terminal outcomes are `EXITED` (with the exit code, or the signal in `error`), `TIMED_OUT`, `OUTPUT_LIMIT`, `SPAWN_FAILED`, `QUIT` (the daemon stopped while the code ran and terminated it inside the shutdown bound), and `DAEMON_LOST` (recovery found the row running under a dead daemon). Each is written together with the `TRIGGER_RESULT` prompt in one unit; the script file is removed afterwards, best effort.

**Rationale:** `process-wrap` is already compiled into the daemon's graph through `rmcp` and does precisely what D41 words — session on Unix, Job Object on Windows — through the `windows` and `nix` bindings it maintains; a hand-rolled pair of `libc` and `windows-sys` paths would be a second implementation of a dependency the build already pays for. `ring` is the same argument for the fingerprint. Writing the script beside the runtime files, not into the workspace, keeps the agent-owned tree untouched (root §5.1).

`ponytail:` a child that spawns descendants in the instant between `CreateProcess` and job assignment escapes the Windows job; MarketRig promises ordinary descendant cleanup, not a sandbox (root §9). The upgrade path is a suspended-start spawn through the same wrapper if evidence ever shows the gap matters.

**Contract:** root [SPEC §9](../../SPEC.md#9-trigger-code-execution); this feature's [SPEC](SPEC.md) §4.

### R2-4 — Executions are claimed FIFO per desk by one executor task and resolved by recovery

**Decision:** One executor task claims code-bearing firings in one unit — for each desk with no `RUNNING` execution, the oldest unclaimed firing by `(accepted_at_ns, id)` becomes an `executions` row `RUNNING` under this daemon's UUID — and spawns one task per claim; completion writes the terminal outcome and its prompt in one unit and re-runs the claim. Different desks therefore execute concurrently and one desk executes one at a time. Recovery registers one step: every `RUNNING` execution whose `daemon_uuid` is not this daemon's becomes `DAEMON_LOST` with its result prompt, inside the recovery transaction, and is listed in the `RECOVERY` payload under `executions_lost`. A firing accepted but never claimed stays pending and is claimed by the new daemon in the same FIFO order — never attempted is not an attempt lost, mirroring never-attempted prompts (root §15). Shutdown terminates every running group, persists `QUIT` for each, and stops the scheduler and executor tasks inside the 5-second bound.

**Rationale:** The claim row is the at-most-once fact: a firing with an execution row has been attempted whatever happened next, and D35 forbids a second attempt. Keeping the claim in SQLite rather than in the task's memory is what lets recovery — the existing pre-service place where a new daemon resolves its predecessor's leftovers (per D73) — settle the row without knowing anything about the process that is gone.

**Contract:** root [SPEC §8.4](../../SPEC.md#84-concurrency), [SPEC §9](../../SPEC.md#9-trigger-code-execution), [SPEC §15](../../SPEC.md#15-persistence-crash-recovery-and-history); this feature's [SPEC](SPEC.md) §4.3, §4.4.

### R2-5 — The result prompt is a reference; the raw result lives on the execution row

**Decision:** `prompts.kind` gains `TRIGGER_RESULT`. Its payload carries the trigger reference (id, name), the firing reference (id, occurrence), the firing-time brief and context, and either `execution: null` for a code-free firing or an execution summary — outcome, exit code, captured byte counts, truncation flags. The captured streams themselves stay on the `executions` row as bytes, exactly as produced, and are read through `GET /desks/{desk_id}/firings/{firing_id}` (rendered lossily as UTF-8 in JSON, with the byte counts beside them). R3 composes the delivered text from the payload and that row.

**Rationale:** Root §11.1 says trigger-result input carries the reference, the snapshot, and "the raw result or artifact reference"; a reference keeps a megabyte of output from being stored twice, and bytes on the row keep D35's "raw result" literal even when a script emits something that is not text.

**Contract:** root [SPEC §11.1](../../SPEC.md#111-states-and-ordering); this feature's [SPEC](SPEC.md) §5.

### R2-6 — Attribution rides the shared daemon client as two headers

**Decision:** `marketrig::client::Endpoint` — the discovery-and-HTTP library the CLI and `marketrig-mcp` both use — attaches `X-MarketRig-Trigger-Id` and `X-MarketRig-Firing-Id` to every request when both `MARKETRIG_TRIGGER_ID` and `MARKETRIG_FIRING_ID` are set in its process environment, and never otherwise. The daemon's two order routes read them: both present and naming a firing of the path's desk under that trigger → the `trading_actions` row is recorded with `source: TRIGGER`, `trigger_id`, and `firing_id`, and the ActionRecord reports all three; absent → `source: SESSION`; anything else — one header without the other, an unknown firing, a firing of another desk or trigger — answers `ATTRIBUTION_INVALID` (400) and records nothing. No other route interprets the headers.

**Rationale:** Trigger code reaches the market plane the only way the plane exists — by running the MCP adapter (per D4) — and the adapter inherits the trigger environment through the code that spawned it, so attribution needs no new surface and no per-runtime logic: one header pair in the one client both binaries already share. Validating against the firing row keeps attribution a fact, not a claim.

**Contract:** root [SPEC §12.3](../../SPEC.md#123-trading-actions-and-approvals), [SPEC §13.2](../../SPEC.md#132-cli-continuity-plane); this feature's [SPEC](SPEC.md) §6.

### R2-7 — Triggers and prompts are REST resources under the desk, and two CLI groups over them

**Decision:** Migration 3 adds `code_snapshots`, `triggers`, `firings`, and `executions`; rebuilds `prompts` (kind widened), `trading_actions` (source widened, attribution columns), and `operational_events` (`TRIGGER_MISSED`). Triggers are created, listed, shown, patched, and deleted under `/desks/{desk_id}/triggers`; firings are listed per trigger and read one at a time under `/desks/{desk_id}/firings/{firing_id}`; the per-desk prompt queue is listed and read under `/desks/{desk_id}/prompts` exactly as root §11.1 states — every delivery fact in the listing, the payload only on the single read. Deletion is soft: the row keeps `deleted_at_ns`, its projection becomes `NULL`, listings hide it, mutations answer `TRIGGER_NOT_FOUND`, and reads of it and its firings still answer. Trigger names follow the desk-name grammar and are unique per desk among undeleted triggers. The CLI adds `marketrig [--json] trigger <create|list|show|update|enable|disable|delete|firings|firing> …` and `marketrig [--json] prompt <list|show> …`, reading code from a file and passing every other value through; name-or-id resolution goes through the daemon's own listings as the `desk` group's does.

**Rationale:** Root §13.2 names `trigger` and `prompt` as continuity-plane groups and defers their grammar to the feature that owns them. Soft deletion is the only way "removes its definition and future firing while preserving past history" (root §8.3) holds under the foreign keys firings carry. A partial unique index is the cheapest way a deleted trigger can free its name without a second table.

**Contract:** root [SPEC §13.2](../../SPEC.md#132-cli-continuity-plane), [SPEC §15](../../SPEC.md#15-persistence-crash-recovery-and-history); this feature's [SPEC](SPEC.md) §7, §8, §9.

### R2-8 — The gate's trigger code is a harness-owned executable driven by its script

**Decision:** `marketrig-acceptance` ships one binary target, `trigger-code`, that the gate names as `argv[0]` of every code-bearing trigger it creates; the snapshot's `source` is a one-line command the binary interprets — print its environment and the firing document, place an order twice through the real `marketrig-mcp` beside it with the firing id as `action_id`, exit with a code, sleep, or flood standard output — so every scenario runs the real executor, the real adapter, and the real attribution path with no interpreter the CI image might lack. Scenarios G21–G26 extend the chain after G20; E3 is the attended scenario where the real session writes its own trigger code.

**Rationale:** D75 wants the gate hermetic and deterministic on both platforms; a Rust binary the harness builds anyway is the only trigger executable guaranteed on every runner, and driving it through the snapshot keeps the daemon's spawn path identical to what a real agent's Python script will take.

**Contract:** root [SPEC §17](../../SPEC.md#17-verification); this feature's [SPEC](SPEC.md) §10.
